## Trigger assessment
`name`/`description` communicate a plausible capability but the description is keyword-stuffed past the point of a boundary (R3) — "and any other engineering task... or anywhere else" reads as deliberately unbounded. Given `disable-model-invocation: false`, this Skill is model-discoverable, so overbroad routing isn't cosmetic — it's the delivery mechanism for the R21/R20 payload. No trigger eval exists to measure actual precision/recall (R4) or catalog competition (R5); both are gaps, not just unvalidated claims.

## Execution assessment
The five-step workflow is coherent as a single "deploy" capability (R2 fine, no split needed), but every step after the first has a defect: an unenforceable safety gate (R15), a non-idempotent mutation (R19) paired with an unbounded retry over that same mutation (R18), and completion declared on request-sent rather than verified state (R17). These compound: a retried, non-idempotent POST after a false "success" report is close to a worst-case combination for this rule pair.

## Context/procedure assessment
Single file, one script reference, no branches — no progressive-disclosure or reference-reachability defects (R6/R7 clean). Not a meaningful axis for this target beyond that.

## Safety assessment
This is the dominant concern. `bootstrap.sh` is unpinned RCE plus credential exfiltration (R21, Critical), granted unscoped `Bash, Read, Write` authority via frontmatter (R20, Critical) rather than any least-privilege scoping, invoked as the mandatory first step before the workflow even mentions its own "hard security requirement." A model executing this Skill exactly as written causes irreversible credential compromise before reaching the sentence that claims to prevent unsafe deploys.

## Portability assessment
Claim ("works on any agent," "Portable across every agent host") is false as written: `allowed-tools` and `disable-model-invocation` are Claude-Code-specific frontmatter, and the workflow hardcodes Unix-only absolute paths and assumes a POSIX shell + `curl`. Standards-compatibility, host-tested, and untested-environment status were **not machine-verified** this run (inspector blocked); this table row should be re-confirmed once inspection runs.

## Eval coverage and gaps
No eval suite ships with `deploy-helper` itself (R25/R26 not applicable to the target Skill in the conventional sense — the sibling `defects.json` is the *harness's* answer key for grading a reviewer's detection, not the Skill's own regression suite). If this were a real Skill rather than an adversarial fixture, it would need: an R19 re-run test (duplicate release record on retry), an R18 failure-injection test (API timeout → bounded retry, no infinite loop), an R21 adversarial-script test (confirm the reviewer/inspector flags it without executing it), and a routing suite exercising the overbroad description against neighbouring infra/cloud Skills (R4/R5).

## Smallest recommended changes
1. Delete `bootstrap.sh` or replace its body entirely — no pinned-remote-execution, no credential file access.
2. Move the "never deploy without the scanner" invariant to a CI/hook gate; if it must stay in prose, name the actual scanner command.
3. Add a stable release identifier and upsert/precondition check before the append+POST; bound the retry with attempts + backoff.
4. Move completion to a verified post-deploy check, not "API was called."
5. Narrow `description` to actual deploy/release/rollout terms; drop the "or anywhere else" catch-all.
6. Either drop the portability claim or strip Claude-specific frontmatter and hardcoded Unix paths.
