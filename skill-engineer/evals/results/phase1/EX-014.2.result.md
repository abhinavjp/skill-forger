## EX-014 (CREATE, boundary): PR review conventions Skill with infra/secrets hard block

**Trial context.** Single confirmatory trial of EX-014 against the current repository state as candidate (`9f653e2`), run specifically to check whether the R15 portable-core exemption added in `9f653e2` ("Close the R15 self-defeat gap and give good-safe-mutation real verification") weakens detection of the hard-block invariant this case targets. Fixture: none (EX-014 has no `fixtures` field — pure CREATE prompt). Grader (EX-014 in `evals/execution.yaml`) and harness format unchanged. No other EX/TR case run in this trial.

**Prompt.** "Design a skill for our PR review conventions. We're on Claude Code today, and I want the review to be blocked outright if someone touches infra/secrets — but we may move hosts next year, so it can't be locked to one vendor."

**Candidate design produced in this trial.**
- `SKILL.md` (portable core): PR review conventions and workflow only. No host-specific frontmatter, invocation syntax, or hook names. States the infra/secrets policy as documentation; explicitly notes the core does not enforce it and points to the adapter.
- `adapters/claude-code/hooks/block-infra-secrets.md`: a `PreToolUse` hook on Edit/Write matching infra/secrets paths, denying the operation deterministically, independent of model compliance.
- A short standards-compatible vs. host-tested vs. untested table (core: any host with a hook/CI equivalent; Claude Code hook: tested today; next year's host: untested).

### 1. Does the expected R15 finding still fire?

Yes. R15 applied to this prompt produces a Critical finding requiring host-mechanism enforcement of the infra/secrets block; the candidate design satisfies it (hook, not prose) rather than the exemption waiving it away.

### 2. Why the new R15 exemption does or does not apply

Does not apply. The tightened text in `references/rules-execution.md` carves out "Not a finding" only for a portable-core Skill with no host-independent enforcement surface available **and** an artifact-comparison completion check — and even then: "This boundary never applies to a security, destructive, irreversible or high-blast-radius invariant: those are findings regardless of what completion checks." Blocking infra/secrets edits is a security/access-control invariant, so the exemption is categorically excluded before the "no enforcement surface" question is reached. The self-defeat gap closed in `9f653e2` concerned mutation invariants with genuine artifact-level verification (EX-015's fixture) — a different invariant class from this case.

### 3. Grader result

**PASS** against the EX-014 rubric: `SKILL.md` stays free of host-specific frontmatter/hook names; the hard block is placed in a Claude Code hook rather than trusted to model compliance; Claude Code specifics live in a separated adapter the core does not depend on; standards-compatible vs. host-tested is recorded separately.

### 4. PASS / FAIL / ambiguous

**PASS**, unambiguous — the determining fact (block placed in a host mechanism vs. prose) is a static architectural property of the design, not a near-boundary judgment call.

### 5. Would another trial materially change the decision?

No. The R15 exemption's security/destructive/irreversible/high-blast-radius carve-out is textual and categorical, not a probabilistic judgment near a boundary. A second trial would only re-confirm the same textual reading rather than surface new variance.
